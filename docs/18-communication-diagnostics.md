# M15 通信诊断说明

## 1. 阶段目标

M15 的目标是让通信层更接近现场联调要求。上位机不仅要能连接模拟器，还要能回答这些问题：

- 当前连接的是哪个端点。
- 请求是否持续收到响应。
- 是否出现超时、错误或重连。
- 最近一次响应耗时是多少。
- 通信质量是否下降。

本阶段仍然以 Modbus TCP 模拟器为对象，不做多 PLC 冗余，也不做复杂网络故障仿真。

## 2. 通信诊断数据

`ModbusTcpClient` 新增 `CommunicationDiagnostics` 诊断快照，包含：

| 字段 | 含义 |
| --- | --- |
| `state` | 当前连接状态 |
| `endpoint` | 当前连接地址和端口 |
| `pendingRequests` | 已发送但尚未收到响应的请求数 |
| `totalRequests` | 请求总数 |
| `totalResponses` | 正常响应总数 |
| `timeoutCount` | 超时次数 |
| `errorCount` | Socket 或协议错误次数 |
| `reconnectCount` | 自动重连次数 |
| `consecutiveTimeouts` | 连续超时次数 |
| `lastRoundTripMs` | 最近一次请求到响应的耗时 |
| `qualityPercent` | 通信质量百分比 |
| `lastRequestAt` | 最近请求时间 |
| `lastResponseAt` | 最近响应时间 |
| `lastError` | 最近错误信息 |

通信质量按已完成请求中的成功响应比例计算：

```text
quality = responses / (responses + timeouts + errors)
```

## 3. 超时与重连策略

每个 Modbus 请求发送时记录事务号和发送时间。客户端周期检查挂起请求：

1. 如果请求等待时间超过 `timeoutMs`，判定为超时。
2. 超时请求会从挂起队列移除。
3. 如果超时的是写命令，上位机会收到命令失败反馈。
4. 连续超时达到阈值后，客户端主动断开当前 Socket。
5. 断开后进入 `Reconnecting` 状态，并按 `reconnectMs` 自动重连。

这样做可以避免现场网络异常时请求队列无限堆积。

## 4. 界面变化

新增“通信诊断”页，显示：

- 连接状态和目标端点。
- 通信质量。
- 挂起请求、请求总数、响应总数。
- 超时次数、错误次数、重连次数。
- 连续超时、最近耗时。
- 最近请求时间、最近响应时间和最近错误。

顶部状态栏也会显示通信质量，例如：

```text
PLC通信：已连接  质量：100%
```

## 5. 验证方式

1. 构建项目：

```powershell
cmake --build build
```

2. 运行烟测：

```powershell
.\scripts\smoke_test.ps1
```

3. 手工验证：

- 启动 `upkun-hmi.exe`。
- 打开“通信诊断”页，确认连接状态变为已连接。
- 主监控页点击“启动”，观察请求数和响应数持续增加。
- 停止模拟器，观察连接状态进入重连，重连次数增加。
- 再启动模拟器，确认连接恢复。
